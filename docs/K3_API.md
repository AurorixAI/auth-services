# K3 «Заявка на демо в 3 шага и одобрение центра» — контракт сервера (auth)

Ветка `k3` (auth-service-p154), пункты A1–A9 из `artifacts/console/K3_SPEC_v2.md`. Версия 1 (29.10.2026), пишется **до** реализации; код и тесты сверяются с этим файлом.
Продолжает `artifacts/console/API_CONTRACT.md` §1 (публичная заявка) и §«заявки» консоли: всё, что здесь не сказано, остаётся как там. Ошибки — `{"detail": "<русский текст>", "code": "<machine_code>", ["fields": {...}]}`.

## 0. Правила

1. Заявка создаётся **на шаге 2** (обязательные поля шагов 1–2); шаг 3 дописывает её по токену. Одна заявка = одна строка = одно письмо команде.
2. **Незнакомые ключи тела → 400, не молча** (A2). Лендинг, выкаченный раньше сервера, получает отказ, а не «принято» с потерянными данными.
3. Письма реально уходят в фоне после ответа; их исход пишется в строку заявки (§5), чтобы консоль показала «письмо не ушло».
4. Пока лендинг не выложен, старая форма продукта (`/request-demo`) тоже работает: она шлёт только прежние поля, поэтому **все новые поля, включая `org_type` и `requestId`, необязательны для сервера**. Обязательность шагов 1–2 обеспечивает форма лендинга. Заявка без `org_type` одобряется как `center` (прежнее поведение).
5. Имена полей: прежние и новые поля заявки — `snake_case`; служебные (`requestId`, `detailsToken`, `turnstileToken`) — `camelCase` (как в ТЗ).
6. Конфиденциальность (L4 отложено владельцем 29.10): `consent_at` хранится, но **не требуется**.

## 1. `POST /api/v1/public/demo-requests` (создание, шаги 1–2)

Без входа. Тело — JSON-объект. Все известные ключи:

| Ключ | Шаг | Тип / правило | Обяз. (для сервера) |
|---|---|---|---|
| `centre_name` | 1 | текст 2..200 | да |
| `org_type` | 1 | один из 6: `center` Учебный центр, `private_school` Частная школа, `university` Университет, `tutoring_center` Репетиторский центр, `tutor` Репетитор, `other` Другое | нет (§0.4) |
| `city` | 1 | текст 2..100 | да |
| `address` | 1 | текст ≤ 300 | нет |
| `students_count` | 1 | целое 0..100000 | нет |
| `branches_count` | 1 | целое 0..999 (0 = филиалов нет) | нет |
| `contact_name` | 2 | текст 2..120 | да |
| `position` | 2 | `owner` / `director` / `admin` / `other` | нет |
| `phone` | 2 | как раньше (+998 в любом виде, другая страна — только с «+»), хранится `+998XXXXXXXXX` | да |
| `email` | 2 | как раньше, хранится в нижнем регистре | да |
| `preferred_contact_time` | 2 | текст ≤ 100 | нет |
| `needs` | 3 | список из `payments` (оплаты и долги), `attendance` (посещаемость), `payroll` (зарплата учителей), `diagnostics` (диагностика), `exams` (экзамены); до 5, повторы схлопываются | нет |
| `current_tool` | 3 | `excel` / `notebook` / `other_system` / `none` | нет |
| `heard_from` | 3 | текст ≤ 200 (свободный, «Другое: …») | нет |
| `comment` | 3 | текст ≤ 2000, переводы строк разрешены | нет |
| `locale` | — | `ru` / `uz` / `en`, по умолчанию `ru` (письма пока только на русском) | нет |
| `consent` | — | `true` → `consent_at` = сейчас; иначе `consent_at` = `null` | нет |
| `source` | — | как раньше: объект из 7 ключей `utm_*`, `referrer`, `landing`, значения ≤ 300 | нет |
| `requestId` | — | uuid, который клиент создаёт **один раз на заявку** (идемпотентность, §1.2) | нет (§0.4) |
| `turnstileToken` | — | токен Cloudflare Turnstile | да, если на сервере задан `TURNSTILE_SECRET_KEY` |
| `website` | — | honeypot: у человека пусто | — |

Поля шага 3 разрешены и в этом запросе (клиент, который отправил всё сразу).

### 1.1 Порядок проверок (A5)

1. Тело не объект → `422 invalid_body`.
2. **Honeypot** (`website` непустой) → `201 {"ok": true, "message": ...}` без записи, без писем, **не расходует ни один лимит**.
3. **Повтор `requestId`** (§1.2) → `200`, без Turnstile, без лимитов, без писем.
4. **Turnstile** (если задан `TURNSTILE_SECRET_KEY`): токена нет или Cloudflare сказал «нет» → `400 captcha_failed`. Cloudflare недоступен (таймаут 5 с, сеть) → заявка **принимается** (в логе предупреждение): потерять настоящую заявку хуже, чем пропустить бота, которого дальше держат лимиты. Ключ не задан → шаг пропускается.
5. **Лимиты** (как раньше): 5/ч с адреса (IPv6 — по /64), 3/ч с почты, 10/ч с домена почты, 60/ч на всю форму → `429 rate_limited` + `Retry-After`.
6. Незнакомые ключи → `400 unknown_fields`.
7. Проверка значений → `422 validation_error` + `fields` (русские тексты).
8. Запись, коммит, ответ; письма — в фоне.

Почему повтор `requestId` стоит до Turnstile и лимитов: токен Turnstile одноразовый, повтор после потерянного ответа с ним не пройдёт; повтор не должен получать «слишком много заявок» за свою же заявку.

### 1.2 Ответы и идемпотентность (A3)

* `201` — новая заявка: `{"ok": true, "message": "Заявка принята. Мы свяжемся с вами в течение 1 рабочего дня.", "id": "<uuid>", "detailsToken": "<токен>", "detailsTokenExpiresAt": "…Z"}`.
* `200` — повтор того же `requestId`: **то же тело**, та же заявка, ни второй строки, ни второго письма; тело повтора игнорируется. Если с создания прошло больше 2 часов, `detailsToken` = `null`.
* Два одновременных запроса с одним `requestId` (двойной клик): выигрывает один (уникальный индекс), второй получает `200` с той же заявкой.
* Повтор с той же **почтой** без `requestId` — по-прежнему новая строка с `is_repeat` (правило K1 не менялось).
* `400 unknown_fields`: `{"detail": "Неизвестные поля в заявке", "code": "unknown_fields", "fields": {"<ключ>": "Неизвестное поле"}}` (до 10 ключей, каждый обрезан до 50 символов).
* `400 captcha_failed`: «Проверка не пройдена. Обновите страницу и отправьте ещё раз.»
* `422`, `429` — как раньше.

### 1.3 `detailsToken` (A4)

Подписанный токен (HMAC-SHA256 от `SECRET_KEY`, отдельный префикс-назначение), внутри — id заявки и время истечения = создание + **2 часа**. В базе не хранится; один и тот же для одной заявки (поэтому повтор `requestId` возвращает его же). Клиент хранит его только в памяти вкладки/sessionStorage.

## 2. `PATCH /api/v1/public/demo-requests/{id}` (шаг 3, A4)

Тело: `{"detailsToken": "...", "needs"?: [...], "current_tool"?: "...", "heard_from"?: "...", "comment"?: "..."}`. Правила значений — как в §1. Допустимы только эти ключи (остальные → `400 unknown_fields`); нужен хотя бы один из четырёх (иначе `422 validation_error`, «Нечего дописывать»).

* `200 {"ok": true, "id": "<uuid>"}`. Поля **заменяются** присланными (повтор запроса безопасен: тот же результат); не присланные остаются. Писем PATCH не отправляет (письмо команде и письмо заявителю уходят один раз, при создании).
* `403 invalid_details_token` — токена нет, подпись не сошлась или токен от другой заявки; `403 details_token_expired` — прошло 2 часа.
* `404 not_found` — заявки нет.
* `409 already_processed` — заявка уже одобрена или отклонена (центр уже создан по тем данным, что были).
* `429 rate_limited` — не больше 20 PATCH в час с адреса.

## 3. Письма заявителю: потолки (A5)

Письмо «Заявка получена» — не больше **1 на адрес в сутки** и не больше **100 писем формы в сутки на всех** (скользящее окно 24 ч). Сверх потолка заявка **сохраняется**, письмо не уходит, у строки `mail.applicant = "cap"`. Письмо команде «Новая заявка» потолком не ограничено (оно идёт на один доверенный адрес; поток ограничен лимитами §1.1).

## 4. Консоль (A7, A8)

Строка списка и карточка `GET /platform/demo-requests[/{id}]` получают поля:

| Поле | Значение |
|---|---|
| `org_type` | код или `null` (подпись — на фронте одной функцией `orgTypeLabel`) |
| `address`, `branches_count`, `position`, `preferred_contact_time`, `needs` (список, `[]` если пусто), `current_tool`, `heard_from`, `locale`, `consent_at` | как в заявке, `null` если не заполнено |
| `mail` | `{"team": "pending"\|"sent"\|"failed"\|null, "applicant": "pending"\|"sent"\|"failed"\|"cap"\|null}`; `null` — заявка создана до K3. `team: "failed"` — подпись «письмо команде не ушло»; `applicant: "cap"` — «письмо заявителю не отправлено: потолок»; `applicant: "failed"` — «письмо заявителю не ушло» |
| `email_in_algo` | `true`, если почта заявки уже есть у пользователя ALGO (считается при каждом чтении, только у открытых заявок: после одобрения почта принадлежит новому владельцу, предупреждения нет). Заявителю об этом не сообщается: его ответ и письмо те же |

`POST /platform/demo-requests/{id}/approve`: центр создаётся с `org_type` **из заявки** (нет в заявке — `center`) и `address` из заявки; остальное как раньше (ответ не менялся). Прежние ошибки `409 already_processed`, `409 email_in_use`.

`GET /platform/orgs/{id}` (карточка центра) получает `org_type` и `request`: `{"id", "created_at", "needs", "current_tool", "heard_from", "branches_count", "position", "preferred_contact_time"}` или `null` (у центра нет заявки-источника).

Письмо «Новая заявка» показывает все новые поля (тип центра словами, адрес, филиалы, должность, удобное время, задачи словами, чем пользуются, откуда узнали, язык). Тексты чужого человека обезврежены, как раньше.

## 5. Колонки `demo_requests` (A1, только добавление, все nullable)

`org_type`, `address`, `branches_count`, `position`, `preferred_contact_time`, `needs` (JSONB-список), `current_tool`, `heard_from`, `locale`, `consent_at`, `request_id` (уникальный частичный индекс), `team_mail_status`, `applicant_mail_status`. Существующие колонки не меняются. CHECK на `org_type` — те же 6 значений, что у `organizations`. Откат — `downgrade` (колонки заявок теряются), код обратно совместим.

## 6. Старт сервиса и окружение (A9)

* `REQUIRE_DIAGNOSTIC_BASE_URL=true` — уже работает (`startup_guard.diagnostic_base_url`): `DIAGNOSTIC_BASE_URL` пустой или localhost при `APP_ENV` staging/production → сервис не стартует.
* **Новая проверка:** при `APP_ENV` staging/production, если хост `FRONTEND_URL` совпадает с хостом `SITE_URL` (продукт и лендинг на одном адресе) — в лог уровня ERROR; сервис **не стартует**, если задано `REQUIRE_DISTINCT_SITE_HOSTS=true`. Флаг включается вместе с A10 (смена `FRONTEND_URL` на `app.`): сейчас на проде и stage хосты совпадают (`algolab.me`, `stage.algolab.me`), жёсткая проверка остановила бы выкладку auth (шаг 3 порядка) до шага 7.
* `TURNSTILE_SECRET_KEY` (необяз.): не задан при staging/production — предупреждение в лог (форму держат только honeypot и лимиты).
