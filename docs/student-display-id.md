# Автогенерация публичных ID учеников (Display-ID)

**Тикет:** Автогенерация публичных ID учеников при онбординге и после диагностики.
**Статус:** базовая версия уже в `main`; данная ветка (`feature/student-display-id-initials`)
— корректирующая PR с финальной схемой префикса. Проверено end-to-end (реальный Postgres).

---

## 0. Обновление (корректирующая PR — читать первым)

Первая версия фичи была смёржена в `main` (PR #1) **раньше времени**, со старой схемой
префикса (первые 4 буквы названия, `AL15-…`). По уточнённому требованию схема изменена, и это
оформлено отдельной PR от актуального `main` (первую миграцию не трогаем — она уже применена).

**Финальная схема префикса — инициалы организации, уникальные между орг-ми:**
- первая буква первых двух слов (`New CastleSchool` → `NC`), одно слово → первые две буквы
  (`Algo` → `AL`); кириллица транслитерируется (`Школа Знаний` → `SZ`);
- если инициалы уже заняты **другой** организацией — числовой суффикс:
  второй `New Crown School` → `NC1`, затем `NC2` …;
- ID ученика: `NC-001`, у коллизии `NC1-001` (дефис обязателен — иначе `NC`+ученик 11 совпал
  бы с `NC1`+ученик 1).

**Что в этой PR:**
- `student_id_service.py` — логика инициалов + коллизия (`ensure_org_prefix`), заменяет старую
  `resolve_prefix`.
- `models/auth.py` — `UNIQUE(organizations.student_id_prefix)`.
- **новая** миграция `f6a7b8c9d0e1` — добавляет этот UNIQUE-индекс (миграцию `e5f6a7b8c9d0`,
  уже смёрженную/задеплоенную, НЕ редактируем).

Разделы 3.1/3.2 ниже описывают исходную (старую) реализацию префикса; актуальна схема из §0.

## 1. Что просили (бизнес-логика)

Для «zero-friction лобби» каждому ученику нужен короткий читаемый ID вида
`[Префикс организации]-[Порядковый номер]`, например `AL15-001`.

ID выдаётся строго в момент **фактического зачисления**, в двух сценариях:

1. **Сейчас — онбординг центра:** при массовом импорте (Excel) уже действующих учеников.
2. **В будущем — новые лиды:** ученик «с улицы» сначала попадает в буфер, проходит
   обязательную диагностику, и ID выдаётся только когда админ нажимает
   «Определить в группу» (перевод в `active`).

## 2. Что выяснилось до начала (важно для ревью)

Прежде чем писать код, обнаружилось расхождение веток, напрямую влияющее на задачу:

| Ветка | Что содержит |
|-------|--------------|
| `origin/main` | Фича массового импорта (`src/auth/import_service.py`, эндпоинты `/org/import/*`), `student_phone` уже nullable. |
| `khamidfixes` | Отдельный фикс диагностики (`correct_answers`, batch-join). **Импорта нет вообще.** |

Ключевые следствия:

- Эта задача **надстраивается над импортом** (сценарий «срабатывание сейчас»), а импорт
  живёт только в `main`. Поэтому фича сделана **на ветке от `main`**, а не от `khamidfixes`.
- Фронт (`algo-front/main`) уже вызывает `/auth/org/import/*` — эти эндпоинты есть только
  в `auth-services/main`. То есть для рабочего end-to-end бэкенд обязан быть на `main`.
- ⚠️ **Коллизия ревизий Alembic:** обе ветки независимо создали миграцию с одним и тем же
  `revision id = d4e5f6a7b8c9`, но разным содержимым. Если `khamidfixes` когда-нибудь
  будут мёржить в `main`, эту коллизию нужно будет разрулить вручную. Наша новая миграция
  (`e5f6a7b8c9d0`) наследуется от версии `d4e5f6a7b8c9`, которая в `main`
  (`add_import_support`).

> Отдельный фикс `correct_answers` из `khamidfixes` в `main` **не входит** — это независимый
> follow-up по диагностике, не относящийся к Display-ID.

## 3. Что сделано

### 3.1. Переиспользуемый сервис (архитектурное требование AC)

Новый модуль **`src/auth/student_id_service.py`** — вся логика генерации вынесена отдельно и
НЕ зашита в контроллер импорта. Зависит только от ORM-моделей, поэтому вызывается из любого flow.

Публичный API:

| Функция / класс | Назначение |
|-----------------|------------|
| `resolve_prefix(org)` | Префикс: явный `org.student_id_prefix` или вывод из названия. |
| `format_display_id(prefix, seq)` | `("AL15", 1) → "AL15-001"` (лидирующие нули, ширина ≥ 3). |
| `assign_display_id(db, org_id, student, *, force=False)` | Выдать ID одному ученику. Идемпотентно. Для `AssignToGroup`. |
| `DisplayIdAllocator(db, org_id)` | Пакетная выдача для импорта: одна блокировка на пакет. |

**Алгоритм (как в тикете):**
1. `SELECT max(sequence_number) WHERE org_id = ?` → `+1`.
2. `display_id = f"{prefix}-{seq:03d}"`.
3. Перед чтением максимума берётся `SELECT ... FOR UPDATE` по строке организации —
   два параллельных импорта не выдадут одинаковый номер.

### 3.2. Подготовка БД (AC: поле sequenceNumber)

`src/models/auth.py`:
- `Organization.student_id_prefix` `VARCHAR(16)` (nullable) — префикс, напр. `AL15`.
- `Student.sequence_number` `INTEGER` (nullable) — порядковый номер внутри организации.
- `Student.display_id` `VARCHAR(32)` (nullable) — готовый публичный ID.
- Уникальность **в пределах организации:** `UNIQUE(org_id, sequence_number)` и
  `UNIQUE(org_id, display_id)`. NULL-ы в Postgres различны → ученики в буфере (без ID)
  ограничение не нарушают.

Оба поля у `Student` — nullable: лид в буфере диагностики ID ещё не имеет.

**Миграция `alembic/versions/e5f6a7b8c9d0_add_student_display_id.py`** (идемпотентная):
добавляет колонки/индексы + **разовый бэкофилл** исторических учеников (нумерация по
`created_at` в рамках каждой организации), чтобы старые списки групп не были пустыми.
Миграция применяется автоматически при старте сервиса (`command.upgrade(cfg, "head")`).

### 3.3. Сценарий импорта — срабатывает сейчас (AC: только Insert)

`src/auth/import_service.py`, секция «3) Students» в `commit()`:
- для каждого **нового** ученика (`action == "create"`) вызывается `allocator.allocate()` →
  проставляется `sequence_number` + `display_id`;
- существующие (`action == "existing"`) **пропускаются** — их ID не перезаписывается;
- аллокатор создаётся лениво (только если есть что вставлять) и берёт блокировку раз на пакет.

### 3.4. Сценарий диагностики — задел на будущее (AC: готов для AssignToGroup)

`assign_display_id(...)` уже вызывается из `AuthService.add_student_to_group` в момент
перевода ученика в `active` (если ID ещё нет). Это и есть реализация «assign to group»-потока
существующим кодом; будущий отдельный контроллер `AssignToGroup` вызовет ту же функцию.

`create_student` (ручное добавление одиночного ученика в буфер, статус `new`) **ID не выдаёт** —
это соответствует бизнес-правилу «ID при зачислении, а не в буфере».

### 3.5. Отображение (AC: ID в API и в списке группы)

- `StudentResponse` (`schemas.py`) → добавлены `display_id`, `sequence_number`.
- `Student.to_dict()` и `AuthService._build_student_response()` → возвращают эти поля.
- `AuthService.get_group_detail()` → в карточках учеников группы есть `display_id`.
- **Фронт (`algo-front`, отдельный PR):** тип `StudentInGroup.display_id` + новая колонка
  **«ID»** в таблице учеников группы (`components/groups/group-student-table.tsx`), моноширинный чип.

## 4. Как это работает теперь

```
Импорт (сейчас):
  Excel → /org/import/commit → на каждого НОВОГО ученика: max(seq)+1 → "AL15-001", "AL15-002" …
                               существующие пропускаются, ID не трогается.

Зачисление после диагностики (будущий поток, код готов):
  буфер (new/diagnosed, без ID) → «Определить в группу» → add_student_to_group →
  status=active + assign_display_id() → "AL15-005".
```

## 6. Оставшиеся вопросы / follow-ups

1. **Уникальность префикса между организациями.** `display_id` уникален **в пределах орг-ии**.
   Если «zero-friction лобби» ищет ученика по ID глобально (без выбора центра), два центра с
   префиксом `AL15` дадут неоднозначность. Рекомендация: гарантировать уникальность
   `student_id_prefix` между организациями (валидация при заведении центра) — отдельная задача.
2. **UI-задание префикса.** Сейчас `student_id_prefix` задаётся в БД/при создании орг-ии;
   при отсутствии выводится из названия. Экран настроек организации для ручного ввода префикса —
   отдельный тикет.
3. **Бэкофилл исторических данных** нумерует ВСЕХ существующих учеников (в т.ч. в статусе `new`),
   чтобы списки не были пустыми. Это осознанный компромисс для уже существующих данных; на
   будущее правило «ID только при зачислении» соблюдается. При желании — сузить бэкофилл.
4. **Коллизия миграции `d4e5f6a7b8c9`** между `main` и `khamidfixes` (см. §2) — разрулить при
   будущем мёрже `khamidfixes`.
5. **Мелочь не по теме:** в `main` `StudentCreateRequest.student_phone` — обязательное
   (в `khamidfixes` уже сделано `Optional`). На Display-ID не влияет, но стоит унифицировать.
